# 埋点上报：范围内显式检查，无埋点直接推进

## 1. 适用性与非阻塞原则

埋点是迁移功能的可观察副作用，按原功能范围迁移，不默认删除，也不强制所有模块实现。沿 GO → 父 MO → 子 MO/任务逐级判断：

| 状态 | 含义 | 控制动作 |
| --- | --- | --- |
| applicable | 源功能有埋点触发/公共提供方/配置，或已批准范围明确要求 | 记录事件与源→目标映射，纳入现有 SPEC/TASK/PATH/ASSERT |
| not-applicable | 已检查范围内源码/调用链，无埋点职责 | 写明理由和源码检查证据；events=[]，正常规划、编码、测试、验收，不创建空埋点任务/用例/SDK依赖 |
| unresolved（仅草稿） | 是否存在、事件语义或职责不明确 | 记录具体问题及负责范围，经父 MO/GO/人工澄清；仅影响相关规划，无关模块继续 |

**N/A 是适用性结论，不是测试 skip，也不是 Yellow。** 没有凭证、后端/观测工具不能用、实现遗漏、或代码准备复用，都不能当作“没有埋点”。有埋点的父模块可以分配没有埋点的子模块；有埋点的子模块可以包含没有埋点职责的普通任务。是否 N/A 由认领范围决定，不从父状态直接继承，也不把一个模块的未知回写全局。

不新增全局 telemetry-ready 门禁、不要求预先安装 SDK/联网/取得密钥、不新增埋点阶段或角色。单模块入口只处理本功能埋点与必要接入，外围公共上报能力保留依赖上下文；不得因此扩成全项目迁移。

## 2. 控制流节点

| 节点 | 显式动作与输出 |
| --- | --- |
| GO 功能发现/切片 | 用例优先且对照源码：检查曝光/点击、业务成功失败、页面/应用生命周期、后台任务、公共 track/report 封装、拦截器/注解/生成接线、配置开关；按项目实际存在项分析。把事件行为列进功能清单、源码来源和模块 scope；无埋点记录 N/A。共享 SDK/队列/参数能力识别提供方与消费者，不机械拆出一个埋点 MO。 |
| GO 模块四维分析 | UI 记录触发入口，Logic 记录参数/条件/频次/副作用，Adhesive 记录 SDK/DI/平台/生命周期真实接线，Resource 仅记录实际配置资源；埋点不是第五个维度。 |
| 父 MO 拆分 | 将已识别事件和公共接入职责完整分配给子 MO；公共能力唯一 owner，业务消费者只接入，不重复造 SDK。子模块可 N/A，不能因父模块存在埋点而强制每个孩子实现。新增/不确定公共边界交人工。 |
| 子 MO / Spec Designer | 在冻结六件套中记录事件契约与验收层级；任务逐项 applicable/N/A。适用事件绑定 TASK、业务 PATH、ASSERT，测试设计读取已审核的存量行为，不能按新实现反推 expected。 |
| Implementer / Fixer | 按冻结任务保留触发时机、事件/参数语义、频次和生产发送链；优先正确复用目标已有能力/二方库，清理已替代冗余，必要平台差异适配。不得以空实现、打印日志或重复调用替代上报。 |
| Test-Runner | 接受代码后先 Build，再通过项目适配器验证事件。普通 UI 路径照常执行；埋点路径使用真实结构化观测，截图/录屏不足以证明事件参数、发送或接收。按每条冻结路径记录三态和回执。 |
| MO / Ledger | N/A 不添加用例、依赖、修复轮次或阻塞状态；有埋点沿现有覆盖/三态/修复/复测链验收。缺口只归属具体模块及真实依赖；不影响独立兄弟。 |
| Auditor | 所有 MO 本轮收尾后，整体审查遗漏/重复事件、错误参数、SDK 接线、复用与公共能力；修改清单列事件→CHG/代码→消费者→CASE/PATH。N/A 核对来源依据即可，不申请埋点环境。有问题再走既有代码治理或 Red/Yellow 闭环，受影响 Green 消费者补回归。 |

## 3. 事件对齐与二方库复用

使用 [埋点分析模板](../../../template/telemetry-analysis.md)。只要求分析实际存在的行为；没有离线队列、采样等机制时写明不适用，不擅自增加功能。

- 源事件 ID/名称 → 目标事件 ID/名称，触发位置、时机/顺序、频次/去重、禁止触发条件。
- 参数名、类型、必填/默认值、取值来源与变换、上下文/用户或会话状态；值脱敏，配置仅记引用，不写凭证。
- 初始化/启用开关、实际已有的授权或用户选择条件、生命周期、线程/异步行为。
- 原项目实际存在的缓存、离线、重试、失败处理、批量、采样等语义；不借迁移修改业务要求。
- 目标已有/二方库 capability、版本、owner、接线入口、适配差异及 fidelity 依据。现有稳定库无需虚构“待完成”的 MO；外部来源默认只读。

日志行、相同 API 名、SDK 编译通过均不是语义等价。事件改名、参数删除、上报策略变化等影响验收时走 CR/澄清冻结，不直接由 Fixer 修改。

## 4. OpenSpec 与机器索引

新规划在 spec/design/tasks/checklist 写适用性，并可使用 `stage-plan.telemetry` 索引：

- 无埋点参照 [stage-plan.json](../../../template/stage-plan.json) 的 not-applicable 示例，填写真实理由/证据，events=[]，全部任务为 N/A，不新增测试路径。
- 有埋点将 [telemetry-contract.json](../../../template/telemetry-contract.json) **整体替换到 stage-plan.telemetry**，填入实际已冻结 TASK/PATH/ASSERT；普通任务也列在 tasks 中，但标 N/A、event_ids=[]。
- `events[].tests` 引用现有业务 PATH/ASSERT（不能用 build）；事件与任务双向关联。事件需要的新增 CASE 先经 GO/MO 覆盖分配，不绕过原权限临时造 ID。
- `telemetry.evidence_refs` / 事件证据引用固化的分析/源码快照，摘要随 plan 冻结；不要绑定即将修改的 live 文件作为永久规划证据。

Ledger 仅在 telemetry 字段存在且非 null 时校验适用性、引用、任务及断言映射；运行时只检查当前计划的证据。旧计划缺该索引不产生新全局阻塞，也不等于证明无埋点：Agent 沿源码/现有 SPEC 核对，发现真实遗漏再走受影响范围的 CR。结构校验不能证明源码事件穷尽或业务断言正确。无需更新全项目计划才能启动无关模块。

## 5. 验收层级与环境缺口

每个事件冻结 `verification_level`，依据需求与存量行为确定，不默认全部要求联网到生产服务：

| 层级 | 证据要求 |
| --- | --- |
| emitted | 真实业务入口触发事件，观测事件名称/参数/次数；不能 mock 被验的事件生成逻辑 |
| sdk-dispatched | 真实生产接线向所选 SDK/发送边界交付事件的结构化回执；普通 print 不足以证明 |
| server-received | 测试接收端/服务端中与本次操作关联的接收记录；仅 SDK 调用成功不足以证明 |

项目 adapter 返回冻结 ASSERT 的 expected/actual 及原始日志/回执证据，沿 execute_test/submit/accept 记录。允许的外部替身边界须先写入 design；只验证 emitted 不能声称 server-received。本包不内置埋点服务或通用网络抓包器，宿主接入已有测试工具；不能用 Harmony 图片断言冒充网络验收。

- **Green**：冻结层级的全部必需断言真实通过；在规范要求禁止上报的场景，观测窗口内“未上报”也应有实际证据。
- **Red**：代码导致漏报/多报、参数/时机/接线错误等真实断言失败；沿现有首轮 Fixer、复测及 memory 处理。
- **Yellow**：缺接收端、凭证、观测能力、超时或无法确认结果；明确哪个事件/层级未验证、根因、owner、下一步，不能标 N/A/Green。

仅部分埋点路径缺环境时，先执行其余可执行业务/埋点路径，提交完整路径集合并保留实际结果；缺测路径单独 Yellow。确认外围原因按现有 audit-defer 留给 Auditor，不用“埋点不可验”覆盖其他 Green。只有整个 automation 环节无法启动且满足既有条件时才用 automation-unavailable/automation-deferred，参见 [构建与自动化分流](build-automation.md)。实际构建/提供方依赖不可用与单纯观测环境缺失分开诊断；不为绕过真实依赖强行 Green。

无埋点从不阻塞迁移；有埋点的真实失败/未知只限制本模块及有证据的依赖，独立任务继续，所有 MO 本轮结束后仍启动 Auditor。缺测不等于验收通过，最终报告保留非 Green 原因和证据。
